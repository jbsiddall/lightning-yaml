This is an executable starting point for the rewrite in
[issue #231](https://github.com/jbsiddall/lightning-yaml/issues/231). Dafny code
creates and reads native JavaScript numbers, booleans, UTF-16 strings, null,
undefined, arrays and plain objects. Values are not placed in datatype wrappers
or copied into a second tree. A ghost heap records graph identity and mutations
for proofs; that metadata is erased from the executed JS.

This is a construction/collection example, not a YAML parser or serializer.
The production parser and its public entry points remain unchanged.

The [recorded gate](../evidence/2026-10-09/native-values-check.txt) includes
verification, strict declarations, the output guard and its mutation tests.

## Run the complete gate

From the research worktree, with the compiler and dependencies installed as
described in the [research README](../README.md):

```bash
bash experiments/dafny-hotpath/native-values/run.sh /path/to/dafny
```

The runner enters the existing bubblewrap sandbox: network disabled, host
read-only, this worktree writable. Then it:

1. Verifies and builds `NativeValues.dfy` with the official JS backend,
   `--unicode-char false`, and `--allow-external-contracts`.
2. Compiles `runtime.ts` and `api.ts`, including declaration emission under strict
   TypeScript settings, and checks a consumer against the emitted declarations.
3. Runs `check-output.cjs` using the explicit roots and extern call sites in
   `guard.json`.
4. Runs the checker regression tests, runtime/boundary tests, and integration
   tests against the actual generated Dafny code. The integration tests inject
   boxing into the generated example and `any` into a declaration to establish
   that those regressions are rejected.

Generated TypeScript output/declarations and mutation fixtures are under the
ignored `dist/` directory. `generated.js` is retained for inspection and is
regenerated by the build. `load.cjs` exposes the generated entry class and binds
the audited host operations using their exact ABI names; sentinel slots remain
immutable.

## Files and roles

| File | Purpose |
| --- | --- |
| `NativeValues.dfy` | External opaque Value type, bounded native Index, external sentinel constants, ghost graph/heap model, construction/access/mutation contracts, and verified examples. |
| `runtime.ts` | Actual JS value operations. Arrays are `[]`, objects are `{}`, primitive conversions return primitives, and identity uses `Object.is`. |
| `api.ts` | Checked consumer-facing facade. Generated results arrive as `unknown`, are checked, then returned without copying. |
| `generated.js` | Official backend output; inspect the example methods, their calls and scalar arithmetic. |
| `load.cjs` | Example binding of the compiled module to the native host operations. |
| `check-output.cjs`, `guard.json` | AST-based regression guard and explicit inspection scope. |
| `build.cjs`, `run.sh` | Combined verification, build, declarations, guard and tests. |
| `runtime.test.cjs`, `api.test.cjs`, `consumer.test.ts` | Host behaviour, malformed-boundary rejection and strict consumer type checks. |
| `integration.test.cjs`, `checker.test.cjs` | Generated-code integration and deliberate failing code-shape fixtures. |

## What a caller uses in Dafny

Use opaque `Value` for native data and bounded `Index` for executable counters.
Keep floating-point data opaque; Dafny `real` is not the JavaScript number ABI.
Existing verified callers require a valid heap, with created/read containers
registered in its ghost graph:

```dafny
var child := CreateObject(h);
var number := NumberFromIndex(h, 7);
ObjectSet(h, child, "number", number);
var values := CreateArray(h);
ArrayPush(h, values, child);
ArrayPush(h, values, child);
ObjectSet(h, child, "self", child);
ObjectSet(h, child, "null", Null);
ObjectSet(h, child, "undefined", Undefined);
```

These operations compile to direct calls such as
`NativeValues.__default.arrayPush(h, values, child)`. The corresponding host
function pushes the same reference into the same native array. There is one
plain context object per heap, with a TypeScript nominal symbol brand, rather
than a context or wrapper around every value. Array/object contents carry no
ghost fields, tags or hidden value wrappers.

`Demo` constructs a native graph with a shared child, a self-cycle, and fields
whose values are actual null and undefined. Its postconditions establish the
graph links and scalar contents relative to the host contracts. `BuildNumbers`
proves the contents of the native numeric array against a ghost integer model;
its executable loop uses JS number arithmetic. `ObjectKeyCount` exercises
native property enumeration and array length.

The native arrays in this interface are dense, bounded in length, and mutable.
`arraySet` replaces an existing element; `arrayPush` grows the array. Reading a
hole is rejected. `objectGet` reads own properties only and returns undefined
for an absent property; use `objectHasOwn` to distinguish absence from a present
undefined value. `objectSet` handles `__proto__` as an own data property without
changing the object's prototype. These semantics are deliberate interface
choices, not all possible JavaScript object behaviours.

## Guard coverage

Run just the output guard after building:

```bash
experiments/dafny-hotpath/sandbox.sh node \
  experiments/dafny-hotpath/native-values/check-output.cjs --manifest \
  experiments/dafny-hotpath/native-values/guard.json
```

The guard reads syntax trees rather than searching comments or string contents.
It rejects explicit TypeScript `any`, BigNumber/BigInt, primitive boxing via
`new Number/String/Boolean/Object`, Dafny runtime collection/coercion references,
and generated datatype constructors on inspected paths. Unknown reachable calls,
unsupported aliases/imports, and missing/ambiguous entry points fail the check.
Named helper calls are followed, so putting boxing into a new helper does not
hide it from a checked entry point.

Ordinary `Array(n)`, array literals, native `Map`/`WeakMap`, and primitive coercion
calls `Number(text)`/`String(value)` are allowed. `Array` is native storage, not a
boxing marker. Creating an array may still be expensive; the guard does not
decide whether an allocation or copy is needed. `any` has no runtime allocation
cost; rejecting it helps maintain the TypeScript boundary.

The manifest explicitly identifies generated entry methods and audited dynamic
calls. It scans host sources, their emitted JS and declarations fully. Generated
runtime/type helpers outside those entry paths are excluded because the compiler
emits them even when unused. Any new public generated entry point must be added
to `roots`; changes to extern calls or their ABI need manifest review. Audited
dynamic receiver calls, such as `array.push`, are trusted manifest boundaries.
The loader/build/test tooling is not part of this hot-path source guard.

This is a syntactic regression guard. It cannot establish allocation freedom,
semantic equivalence, JIT behaviour, or benchmark parity. It does not measure
the startup cost of Dafny's emitted runtime, the shipped bundle or the extern
dispatch cost. Keep code inspection, meaningful allocation/throughput benchmarks
and Dafny verification as separate gates. The checked facade's numeric-array
validation itself costs a traversal and must be measured before production use.

## Exact object literals and compiler customization

The current parser creates `{}` and adds discovered keys through `storeKey`
in [core.ts](../../../src/core.ts). Its flow/block mapping paths do not require
factories containing fixed named properties. A future fast path for a known
shape can use a small TS extern that returns an exact native literal:

```ts
function createHello(value: NativeValue): NativeRecord {
  return { hello: value };
}
```

Specify its allocation, own properties and frame effects in Dafny just like
`CreateObject`/`ObjectSet`, then audit the host implementation. This avoids
per-value wrappers, but retains a call boundary. Measure property order,
prototype behaviour, allocation and dispatch costs before adopting a factory.
For arbitrary keys, preserve the special handling of `__proto__`; its ordinary
literal syntax changes the prototype rather than creating an own data property.

Official Dafny supports .NET plugins loaded with `--plugin`. In the pinned
compiler, [PluginConfiguration](https://github.com/dafny-lang/dafny/blob/v4.11.0/Source/DafnyCore/Plugins/PluginConfiguration.cs)
provides AST rewriters, custom executable backends and compiler instrumenters.
[PreResolve](https://github.com/dafny-lang/dafny/blob/v4.11.0/Source/DafnyCore/Plugins/Rewriter.cs)
can transform Dafny syntax before resolution/verification.
[CompilerInstrumenter](https://github.com/dafny-lang/dafny/blob/v4.11.0/Source/DafnyCore/Plugins/CompilerInstrumenter.cs)
receives the backend and generator, but explicitly has no uniform interface
for changing individual emitted expressions. The
[JS generator](https://github.com/dafny-lang/dafny/blob/v4.11.0/Source/DafnyCore/Backends/JavaScript/JavaScriptCodeGenerator.cs)
is internal to DafnyCore, so directly subclassing it from a separate plugin is
not available without a compiler change. A custom backend or compiler patch
can implement emission rules; no such plugin has been built in this experiment.

The [official plugin documentation](https://dafny.org/latest/DafnyRef/DafnyRef.html)
marks the API experimental and requires plugins to be rebuilt against their
Dafny binary. Pin the compiler/plugin together. A rewrite before verification
can expose extern assumptions to the verifier; custom emission and subsequent
JS rewrites extend the trusted translation boundary and need equivalence checks.

At the audited community exporter revision, its
[CLI](https://github.com/metareflection/dafny2js/blob/61d181fea579f40e6d782a1f8f60cbdcf4562a36/Program.cs)
selects built-in emitters and its
[type mapper](https://github.com/metareflection/dafny2js/blob/61d181fea579f40e6d782a1f8f60cbdcf4562a36/TypeMapper.cs)
implements fixed conversions. We found no converter registration interface in
those paths. Changing its converters currently means editing/forking that
generator; it still wraps the official compiled JS rather than replacing the
compiler's loop emission.

## Proof and compatibility boundaries

- JavaScript extern contracts are assumptions. Tests check the actual host code;
  Dafny proves callers relative to the contracts. Track/audit each assumption.
- Heap effects are explicit through `modifies h` and frame postconditions.
  Type classification, primitive meanings and array/object contents live in
  ghost maps. Equal values are interpreted with `Object.is`; executable opaque
  equality is intentionally unavailable, avoiding Dafny's runtime equality
  protocol for native objects. Structural equality needs its own specification.
- `ParseNumber` and `StringifyNumber` currently call JS `Number(text)` and
  `String(value)`. They preserve native representation, including nonfinite
  numbers and signed zero during parsing, but do not implement YAML numeric
  grammar or formatting. In particular `String(-0)` is `"0"`. The contracts
  establish number classification, not exact floating-point/lexical semantics.
  Add specified native operations when arithmetic on decoded doubles is needed;
  do not route them through Dafny exact rationals.
- `ObjectKeys` proves key membership and count. JS enumeration order is not
  captured in the current ghost model; order-sensitive stringify needs more
  state/contracts.
- This proof example covers constructor-owned data. Existing caller graphs,
  callbacks, proxies, accessor properties, sparse arrays and consumer mutations
  require a specified import/snapshot boundary and appropriate supported-domain
  checks before using the same heap contracts. They can still be passed as native
  references; a boundary model must describe what the code actually observes.
- There is no native/verified YAML compatibility claim yet. Continue the existing
  conformance and differential suites when integrating these operations into the
  real parser/stringifier.
